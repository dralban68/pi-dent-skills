# dx repository standard

These rules apply when the repository's `AGENTS.md`, or your task brief, contains the line `This repository follows the dx repo standard.`; otherwise ignore them, except this one: when you dispatch an agent into a repository whose `AGENTS.md` has that line, put the line at the end of its brief; the brief's first sentence says what the agent is to do.

- `specs/` is the source of truth. A behavior change is a spec change first; an implementation must not deviate from its spec: close or narrow the gap in the spec instead. Load `dx:writing-specs` before writing or changing a spec.
- Terms, when the session has the `Terms` tool: call its `find` action to learn what a domain term means (before qmd or grep) and before writing one in any Markdown file; change entries only through its actions, never by editing its storage file.
- Done in a feature worktree: the tests covering the change pass (`node --test <files>`, or the repository's way of running chosen test files), and `oxlint` and `oxfmt --check` pass on the changed files. Never run `pnpm check` or another full-repository check in a worktree.
- Done on main: `pnpm install --frozen-lockfile && pnpm check` is green and, when the session has the `Terms` tool, its `check` reports no findings. Run them after a merge only when `wt list` shows no other worktree of the same parallel work still to merge; the session that merges the last one runs them. Fix a `pnpm check` failure in a new worktree.
- With the baseline toolchain, the linter bans `as`, `any` and non-null assertions outside `test/**`: convert with a type guard or narrow the declaration. `noUncheckedIndexedAccess` makes index access `T | undefined`; `erasableSyntaxOnly` rules out enums, parameter properties and namespaces.
- No silent failure. Every input skipped, cut off, refused or failed is reported to whoever asked: the user in the UI, or the caller as an error. A `catch` reports or rethrows, never just carries on, and a limit that is reached says so. Prefer streaming and incremental work over a cap that drops data.
- Install with pnpm only; never run `npm install` or commit a `package-lock.json`.
- Be brief in specs, code, comments and replies; do not restate what the code says.
- Develop each feature in its own worktree and branch, made with Worktrunk: `wt switch --create <branch> --no-cd -y` from the repository (its one project hook installs and builds, so the worktree is fully operational), then `wt list` for its path. Work, run checks and commit only there: give that path as `cwd` to every command and dispatched agent, and use absolute paths. Never commit on the main branch's checkout, and never switch its branch; the one exception is `Terms`, which sees only the main checkout: after the feature merges, run its `check` there and commit its operations and the fixes for its findings on main.
- Commit frequently: one commit per logical task, once that task is done. After a spec or code review, once its accepted findings are fixed and committed, commit an empty checkpoint (`/dx:spec-review` and `/dx:code-review`, Checkpoint) so the next review can cover only what changed since.
- When the feature is done and every change is committed, run `wt merge --no-squash` in its worktree: it rebases onto main, fast-forwards main, and removes the worktree and branch, running no checks. Resolve a rebase conflict in the worktree and run it again. A refusal over uncommitted changes in the main checkout means another session's work: resolve it with that session.
- Other sessions share the main checkout and may share your worktree. Never run `git stash`, `git reset --hard`, `git checkout -- <path>`, `git restore` or `git clean` there: they take other sessions' uncommitted work with them. Commit only your own files, by path. When another session's changes are in your way, conflict with yours, or break a check, resolve it with that session (through `Fleet` when the session has it: `list` to find it, `send` or `query` to agree) instead of reverting or overwriting its work.
